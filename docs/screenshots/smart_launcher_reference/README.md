# Smart Launcher 5 — UX reference

Captured 2026-09-02 from `ginlemon.flowerfree` (premium unlocked), emulator-5556,
for scoping portal_launcher's UX pass (icon theming, gesture navigation, home
widgets, drawer/grid layout). Reference only — nothing here was installed for
portal_launcher's own QA pass. Smart Launcher is currently still set as
emulator-5556's default home (left that way mid-exploration, on request —
not reverted this round); portal_launcher's own default-home state is
unaffected since it's a separate package. Read this instead of reinstalling
the app.

## Structural takeaways for the portal_launcher plan

- **Icon theming** = icon-pack picker + an adaptive-shape grid + folder tinting. Self-contained, no dependency on the rest of the app — safe to build in isolation.
- **Gestures** = a small fixed action space (4 directions × N finger-counts) bound through one categorized picker (system actions / navigate to a page / launch an app / launch a shortcut). The category list is the reusable piece — portal_launcher's profiles could plug in as their own action category ("switch to profile X") alongside SYSTEM/NAVIGATION/APPS.
- **Drawer/grid layout** = numeric stepper + labelled sliders w/ reset, all against a live preview using real installed apps. Straightforward Compose port.
- **"Home widgets" in Smart Launcher is two separate things, now screenshotted end-to-end (`27`–`37`):** (1) real, standard Android widgets — `AllowBindAppWidgetActivity`'s OS consent dialog (`30`), provider config activities (`31`), live content immediately on placement (`32`) — the genuine `AppWidgetHost` integration every launcher needs; and (2) their own "Smart Widgets" (`27`, `33`–`35`) — visually richer, several premium-gated, but functionally simpler: no host binding, no provider config, just an app-icon/shortcut assignment flow per slot. (2) is a bespoke home-screen-tile system, not a widget host — building it is a UI/data-model project, not an Android-integration one. Confirmed against the actual portal_launcher codebase (see the plan): **(1) is already fully built** — `widgets/LauncherWidgetHost.kt`, `WidgetPlacement.kt`, `ui/launcher/WidgetViews.kt`, per-profile storage, orphan-id cleanup, the works. Nothing to add there; (2) would be new scope if wanted at all.
- **Search (`38`–`39`) is a fifth area the original 4-item scope missed**: one full-screen search page federating local app match, app-shortcuts, on-device file search, and web/store/video/maps fallbacks — each source permission-gated inline with an explanation, same pattern as onboarding (`01`). Not requested in the original UX scope, flagging in case it's wanted.
- **Correction from the first pass:** Smart Launcher's "pages" (home/drawer/search/feed, `14-page-manager.png`) are fixed canvas types, not named contexts — that part still has no analog. But the **App page's category bar** (`19`–`26`) is a real, closer analog: a user-defined, user-editable, icon-labelled set of named groups that filter which apps show. The structural difference from Portal's profiles: Smart Launcher's categories all coexist as tabs *within one drawer* (switching category never hides a widget or changes the home canvas), where Portal's profiles each own their *entire* app-set and can be swapped wholesale, on a schedule, changing what the whole home screen shows. Worth stealing directly: the **category bar as a UI pattern** (icon + label tabs, add/search/suggested-list flow, empty-state copy, drag-to-reassign) for *how a profile is edited/browsed*, even though *what switching a profile does* (whole-screen swap, not a drawer filter) stays Portal's own, already-ahead model — and is exactly the wedge for "granular personalisation for automations."
